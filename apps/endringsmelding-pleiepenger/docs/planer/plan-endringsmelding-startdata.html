Plan: startdata for endringsmelding fra backend

Fase 2 (plan). Endringsmelding pleiepenger (sif-brukerdialog) og k9-sak-innsyn-api. 9. november 2026.

Mål

Backend avgjør om bruker kan bruke endringsmeldingen, og returnerer saken og arbeidsgiverne i samme svar. Frontend slutter å vurdere tilgang selv.

Vi gjør dette fordi frontend og backend i dag har hver sin kopi av reglene. Etter 30 dager med sammenligning er det ett avvik. Det skyldtes ulik rekkefølge på regler for formatfeil og flere saker. Når bare backend vurderer, er reglene samlet ett sted, og frontend kan ikke velge en annen sak enn den backend vurderte.

Bakgrunn og funn

Denne seksjonen samler det vi fant før planen ble laget, slik at en ny sesjon kan starte fra samme sted.

Avviket som startet arbeidet

tilgangVerifisering.avvik frontend(kanBruke=false årsaker=[harUgyldigK9FormatSak]) backend(kanBruke=false årsaker=[harMerEnnEnSak])

Avviket ble logget av verifiserTilgangMotBackend i frontend. Det er det eneste avviket på 30 dager. Brukeren ble stoppet av begge, men fikk ulik melding.

Årsaken er ulik regelrekkefølge. Brukeren hadde minst to aktuelle saker, og minst én av dem hadde ugyldig format, mest sannsynlig fordi barnet manglet identitetsnummer.

Frontend mapper backend-koden barnManglerIdentitetsnummer til harUgyldigK9FormatSak før sammenligningen. Frontend fanger flere formatfeil enn backend, fordi verifyK9Format validerer hele saken og stopper på første feil. Backend leser saken typet og kjenner bare manglende identitetsnummer på barnet.

Regler avklart med teamet

  • Brukeren skal ikke stoppes hvis det ikke er nødvendig. Mangler barnet identitetsnummer, får det vanligvis nummer i løpet av noen dager.
  • Har brukeren én sak der barnet mangler identitetsnummer og en annen sak som er for gammel, skal brukeren få meldingen om manglende identitetsnummer. Er den andre saken aktuell, skal brukeren få meldingen om flere saker. Det er rekkefølgen backend har i dag.
  • En sak med ugyldig format er fortsatt en sak, og den teller med så lenge vi kan avgjøre hvilken periode den gjelder.
  • Vi retter ikke rekkefølgen i frontend, fordi frontend-reglene skal erstattes av backend.

Tilstanden i koden i dag

  • Frontend henter saker fra innsyn/sak (k9-sak-innsyn-api), validerer dem med verifyK9Format og deler dem i aktuelle og eldre i sakerEndpoint. Deretter kjører tilgangKontroll fase 1 (vurderSaker). Arbeidsgivere hentes fra oppslag/arbeidsgiver via psb-API-et med inkluderAlleAnsettelsesperioder=true, og så kjører fase 2 (vurderArbeidsforhold). Spesifikasjonen står i src/app/tilgang/README.md.
  • Backend-svaret hentes av hentBackendTilgang bak toggle SIF_PUBLIC_HENT_TILGANG_FRA_BACKEND og brukes bare til avvikslogging. Feil fra backend svelges.
  • Backend har koden i no.nav.sifinnsynapi.soknad.endringsmelding.tilgang: EndringsmeldingTilgangController, EndringsmeldingTilgangService, VurderSaker.kt, VurderArbeidsforhold.kt, SakForTilgang.kt og TilgangResultat.kt. Servicen henter saker med innsendingService.slåSammenSøknadsopplysningerPerBarn() og mapper dem til SakForTilgang. Da mister den koblingen til den rå saken.
  • Arbeidsgivere i backend hentes med OppslagsService.hentArbeidsgivere. arbeidsgivereUrl ber bare om organisasjonsnummer og ansettelsesperiode, altså ikke navn. Frontend trenger navnet.
  • Backend gir 5xx når en søknadsperiode mangler fom eller tom, når en ansettelsesperiode mangler fom, og når arbeidsgiveroppslaget feiler eller gir tomt svar.
  • lesSøknadsperioder i frontend returnerer undefined både for tom periodeliste og for perioder som ikke kan leses.
  • /tilgang brukes også av andre, og de trenger ikke mer enn dagens svar.
  • Frontend-felt som ikke trengs: antallSakerFørEndringsperiode ligger i InitialData og SøknadContextState, men ingen leser det. ingenTilgangMeta (erArbeidstaker, erFrilanser, erSN) går bare til analytics og brukes nesten ikke.

Praktisk for neste sesjon

  • Backend-repoet er navikt/k9-sak-innsyn-api, og det er ikke sjekket ut lokalt. I cplt-sandkassen er gh api mot andre repoer blokkert, men GitHub MCP (get_file_contents) fungerer.
  • Playwright-tester kjører utvikleren selv. Ikke kjør pnpm install.

Kontrakt

Forslag til sti: GET /soknad/psb/endringsmelding/startdata. Samme TokenX-krav og Cache-Control: no-store som /tilgang.

{
  "kanBruke": true,
  "årsaker": [],
  "endringsperiode": { "fom": "2026-08-01", "tom": "2027-11-30" },
  "saker": [
    {
      "oppslagsperiode": { "fom": "2026-08-01", "tom": "2027-03-31" },
      "sak": { /* rå k9-format, som innsyn-endepunktet for saker */ },
      "arbeidsgivere": [
        { "organisasjonsnummer": "947064649", "navn": "Snill torpedo", "ansattFom": "2020-01-01", "ansattTom": null }
      ]
    }
  ]
}

Ved avslag: kanBruke: false, minst én årsak og tom saker.

Backend (k9-sak-innsyn-api)

1. Hent navn på arbeidsgiver

Legg til arbeidsgivere[].organisasjoner[].navn i arbeidsgivereUrl og navn: String? i OrganisasjonOppslagDTO. Frontend viser navnet i dialogen. /tilgang merker ikke endringen.

2. Vurderingen returnerer valgt sak

SakForTilgang skal fortsatt være uavhengig av k9-format. Servicen holder parene (SøknadDTO, SakForTilgang) og finner tilbake til rå sak ut fra hvilken sak vurderSaker valgte. Bruk ikke likhet på SakForTilgang til oppslaget. Den er en data class, og to saker med like felt vil kollidere.

3. Felles intern vurdering

data class Endringsmeldingsvurdering(
    val resultat: TilgangResultat,
    val sak: SøknadDTO?,                // bare ved tilgang
    val oppslagsperiode: Datoperiode?,
    val arbeidsgivere: List<OrganisasjonOppslagDTO>,
)

vurder() returnerer dette. vurderTilgang() returnerer vurder().resultat, så /tilgang oppfører seg som før. /tilgang skal ikke slettes, fordi andre fortsatt bruker det.

4. Ny controller

Mapper Endringsmeldingsvurdering til kontrakten over. Saken serialiseres på samme måte som i innsyn-endepunktet for saker, så frontend får samme format.

Frontend (endringsmelding-pleiepenger)

PR 1: nytt endepunkt bak toggle

  • Nytt endpoint-modul for startdata. Kjør verifyK9Format og parseK9Format på saken. Gir de feil når backend har gitt tilgang, vises feilsiden og hendelsen logges.
  • Map årsakskodene til IngenTilgangÅrsak. En ukjent kode skal gi generell melding, ikke krasj, slik at backend kan legge til årsaker uten å vente på frontend.
  • Ny årsak barnManglerIdentitetsnummer: enum-verdi, egen case i IngenTilgangPage, ny story og ny tekst i appMessages.
  • fetchInitialData: når toggle er på, hentes søker og startdata parallelt. Deretter valideres mellomlagringen mot sak og arbeidsgivere fra svaret.
  • Ny toggle, for eksempel SIF_PUBLIC_STARTDATA_FRA_BACKEND. Avviksloggingen fortsetter så lenge toggle er av.
  • MSW-handler for startdata, slik at dev og Playwright bruker samme flyt.

PR 2: opprydding etter stabil drift i prod

  • Fjern tilgang/ (regler, lesSøknadsperioder, ingenTilgangMeta), tilgangKontroll, verifiserTilgangMotBackend og arbeidsgivereEndpoint.
  • Fjern sakerEndpoint hvis ingenting annet bruker det.
  • Fjern antallSakerFørEndringsperiode og ingenTilgangMeta fra typer, context og storybook.
  • Flytt reglene i tilgang/README.md til backend-repoet, der reglene nå bor.
  • Fjern begge togglene.

Oppryddingen gjelder bare frontendens bruk av /tilgang. Selve endepunktet i backend skal ikke slettes, fordi andre fortsatt bruker det.

Utrulling og rollback

  1. Deploy backend. Endringen legger bare til, så det er trygt alene.
  2. Deploy frontend med toggle av. Ingen endring for brukerne.
  3. Slå på toggle i dev og test hele flyten. Det gjelder også mellomlagret søknad fra før byttet.
  4. Slå på i prod. Følg med på feilrate og fordelingen av årsaker i en uke.
  5. Opprydding (PR 2).

Rollback: slå av toggle. Frontend-reglene ligger der til PR 2 er merget.

Observability

  • Backend logger allerede endringsmelding_tilgang_vurdert med første årsak. Legg til hvilket endepunkt som ble brukt, slik at startdata og /tilgang kan skilles.
  • Frontend logger når saken med tilgang feiler verifyK9Format. Det skal være sjeldent. Skjer det ofte, godtar backend formater frontend ikke tåler.
  • Følg med på 5xx-raten på det nye endepunktet etter at toggle er slått på i prod.
  • Ingen saksdata eller identitetsnummer i logg, verken i backend eller frontend.

Sikkerhet og personvern

Svaret inneholder de samme saksdataene som brukeren allerede får fra innsyn-endepunktet, og ingen nye mottakere får dem. Det nye er arbeidsgivernavn, som brukeren også får fra oppslag i dag. Endepunktet tar ingen parametere, så bruker kan bare få egne data. TokenX-kravet og accessPolicy er uendret.

Rød sone

Disse delene bør du skrive selv. Jeg lager testskjelett og stubber hvis du vil:

  • Backend: koblingen fra valgt SakForTilgang tilbake til rå SøknadDTO (punkt 2).
  • Backend: vurder() og at /tilgang gir samme svar som før (punkt 3).
  • Frontend: tolkningen av svaret i fetchInitialData. Det gjelder kanBruke mot antall saker, ukjente årsaker og feilsiden ved formatfeil.

Grønn sone: navn i oppslag, controller og DTO, enum og IngenTilgangPage, MSW-handler, toggle og oppryddingen i PR 2.

Åpne punkter

  • Tekst for barnManglerIdentitetsnummer. Du må gi meg ordlyden.
  • Endringsperioden. Frontend regner den i dag ut fra nettleserens klokke. Backend bruker Europe/Oslo. Jeg anbefaler at frontend bruker perioden fra svaret, så oppslagsperioden og dialogen bygger på samme periode. Det krever at vi finner alle steder som bruker tillattEndringsperiode.
  • Sti for endepunktet. Forslaget over følger mønsteret for /tilgang, men må sjekkes mot Routes.
