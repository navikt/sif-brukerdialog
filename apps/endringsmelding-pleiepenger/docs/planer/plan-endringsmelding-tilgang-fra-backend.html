Plan 1: tilgang til endringsmeldingen avgjøres i backend

Oppdatert etter implementering. Endringsmelding pleiepenger (sif-brukerdialog). Erstatter planen om startdata. 10. november 2026.

Mål

Frontend slutter å vurdere om bruker kan bruke endringsmeldingen. Den bruker svaret fra det eksisterende endepunktet /tilgang i k9-sak-innsyn-api i stedet. Backend trenger ingen endring.

Frontend og backend har i dag hver sin kopi av reglene. Etter 30 dager med sammenligning er det ett avvik, og det skyldtes ulik rekkefølge på reglene for formatfeil og flere saker. Når bare backend vurderer, finnes reglene ett sted.

Relaterte planer

  • Plan 2: saker fra k9-sak-innsyn-api. Bytter datakilde for saker fra sif-innsyn-api, som skal erstattes. Uavhengig av denne planen.
  • Mulig plan 3: egen DTO for saksopplysninger, så frontend slipper å lese rå k9-format. Vurderes etter plan 1 og 2, eller sammen med en v2-migrering av appen.

Regler avklart med teamet

  • Brukeren skal ikke stoppes hvis det ikke er nødvendig. Mangler barnet identitetsnummer, får det vanligvis nummer i løpet av noen dager.
  • Har brukeren én sak der barnet mangler identitetsnummer og en annen sak som er for gammel, skal brukeren få meldingen om manglende identitetsnummer. Er den andre saken aktuell, skal brukeren få meldingen om flere saker. Det er rekkefølgen backend har i dag.
  • Vi retter ikke rekkefølgen i frontend, fordi frontend-reglene skal fjernes.

Tilstanden i koden før endringen

  • Saker hentes fra innsyn/sak i sif-innsyn-api. Den kaller /soknad i k9-sak-innsyn-api og sender svaret videre. /tilgang vurderer de samme sakene, fordi begge bygger på slåSammenSøknadsopplysningerPerBarn.
  • sakerEndpoint kjører verifyK9Format og parseK9Format per sak og deler sakene i aktuelle og eldre. Saker med formatfeil blir klassifisert med lesSøknadsperioder.
  • tilgangKontroll kjører vurderSaker, henter arbeidsgivere for oppslagsperioden og kjører vurderArbeidsforhold.
  • /tilgang hentes av hentBackendTilgang bak toggle SIF_PUBLIC_HENT_TILGANG_FRA_BACKEND og brukes bare til avvikslogging. Feil fra backend svelges.
  • Svaret fra /tilgang er { kanBruke, tillattEndringsperiode?, årsaker }. tillattEndringsperiode er bare satt ved tilgang. Backend bruker Europe/Oslo, frontend bruker nettleserens klokke.
  • Årsakene i backend er de samme som i frontend, med to unntak. Backend har barnManglerIdentitetsnummer, frontend har harUgyldigK9FormatSak.
  • Feltene antallSakerFørEndringsperiode og ingenTilgangMeta brukes ikke eller nesten ikke. /tilgang returnerer ikke grunnlaget for ingenTilgangMeta.
  • /tilgang brukes også av andre og skal ikke endres eller slettes.

Praktisk for neste sesjon

  • Backend-repoet er navikt/k9-sak-innsyn-api, og det er ikke sjekket ut lokalt. I cplt-sandkassen er gh api mot andre repoer blokkert, og get_file_contents i GitHub MCP feilet 10. november. Kodesøket i GitHub MCP fungerer.
  • Playwright-tester kjører utvikleren selv. Ikke kjør pnpm install.

Flyt i fetchInitialData

  1. Hent søker og /tilgang parallelt.
  2. Er kanBruke false, kast IngenTilgangError med årsakene fra backend.
  3. Hent saker og velg de gyldige sakene som ikke er eldre enn endringsperioden fra backend.
  4. Er det ikke nøyaktig én slik sak, logg antall gyldige, aktuelle og ugyldige saker. Er ingen aktuelle og minst én ugyldig, gi harUgyldigK9FormatSak. Ellers feilside.
  5. Regn ut oppslagsperioden med getOppslagsperiode og hent arbeidsgivere.
  6. Valider mellomlagringen med hentGyldigLagretSøknadState, som før.

Frontend (endringsmelding-pleiepenger)

Én PR:

  • Hent /tilgang uten å svelge feil, med appens eksisterende klient mot k9-sak-innsyn-api. Den genererte SDK-en tas i bruk i plan 2.
  • Map årsakskodene til IngenTilgangÅrsak. Ukjent kode blir ukjent.
  • Ny årsak barnManglerIdentitetsnummer: enum-verdi, egen case i IngenTilgangPage, story og tekst i appMessages.
  • sakerEndpoint returnerer gyldige saker og antall ugyldige, uten å dele dem i aktuelle og eldre.
  • getOppslagsperiode og erSakEldreEnnEndringsperiode er flyttet til utils/endringsperiode.
  • Fjernet tilgang/ med vurderSaker, vurderArbeidsforhold, lesSøknadsperioder og ingenTilgangMeta. Også tilgangKontroll, avviksloggingen mot backend og togglen SIF_PUBLIC_HENT_TILGANG_FRA_BACKEND er borte.
  • Fjernet antallSakerFørEndringsperiode og ingenTilgangMeta fra typer, context og Storybook.
  • MSW-handler og Playwright-mock for /tilgang per scenario, slik at dev og Playwright bruker samme flyt.

Endepunktet /tilgang i backend skal ikke slettes, fordi andre fortsatt bruker det.

Utrulling og rollback

  1. Test hele flyten i dev. Det gjelder også mellomlagret søknad fra før byttet.
  2. Deploy til prod. Følg med på feilraten og loggen fetchInitialData.fantIkkeSak i en uke.

Rollback: revert av PR-en.

Observability

  • Logg når frontend ikke finner nøyaktig én gyldig aktuell sak etter at backend har gitt tilgang. Det skal være sjeldent. Skjer det ofte, er frontend og backend uenige om sakene.
  • Logg feil fra /tilgang med logApiError.
  • Backend logger allerede endringsmelding_tilgang_vurdert med første årsak. Den viser fordelingen av årsaker.
  • Ingen saksdata eller identitetsnummer i logg.

Sikkerhet og personvern

Ingen nye data og ingen nye mottakere. Appen kalte allerede /tilgang, og svaret inneholder ikke persondata. TokenX-krav og accessPolicy er uendret.

Rød sone

Disse delene bør gås nøye gjennom i review:

  • Tolkningen av /tilgang i fetchInitialData: avslag, ukjente årsaker og feil.
  • Valget av sak etter tilgang, og antakelsen om at en ugyldig sak er den aktuelle når ingen gyldige er det.

Åpne punkter

  • Reglene fra tilgang/README.md er slettet fra frontend. Vurder om de skal dokumenteres i backend-repoet.
